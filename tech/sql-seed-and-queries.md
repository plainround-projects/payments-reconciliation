# SQL walkthrough: the seed data and the queries, line by line

## What it is

This note reads `sql/002_seed.sql`, which loads the chart of accounts and one small sample day, and `sql/003_queries.sql`, the ten queries of the lesson. These use **DML** (data manipulation: `INSERT`) and **queries** (`SELECT`). It is the companion of `sql.md` and `psql.md`.

## Why this repository uses it

The queries need data to show something, and the sample day makes `make reconcile-sample` find one fee discrepancy without running the full simulation. The queries are the lesson's way of looking at the ledger directly, and several of them are invariants that must return nothing.

## Where it appears

| File | What it is |
| --- | --- |
| `sql/002_seed.sql` | The accounts and the sample day. |
| `sql/003_queries.sql` | The ten lesson queries. |

## How it works underneath

An `INSERT` adds rows; a `SELECT` reads them. `GROUP BY` collapses rows into groups and aggregate functions (`count`, `sum`, `array_agg`) summarize each group; `FILTER (WHERE ...)` limits an aggregate to some rows; `HAVING` filters groups after grouping. A `JOIN` combines rows of two tables on a condition; `LEFT JOIN` keeps rows with no match. `psql` runs a file statement by statement and understands its own backslash commands such as `\echo`.

### `sql/003_queries.sql` (58 lines)

```sql
-- 003_queries.sql: the queries the lesson runs. Run with `make queries`.
```

The queries the lesson runs, with `make queries`. Lines that start with `\echo` are not SQL: they are commands of the `psql` client, which prints the text after them, so the output is labeled.

```sql
\echo '== 1. Trial balance: the raw sum and the balance on its normal side, per account'
SELECT a.code AS account,
       a.normal_side,
       COALESCE(sum(p.amount_minor), 0) AS raw_sum_minor,
       COALESCE(sum(p.amount_minor) * CASE a.normal_side WHEN 'DEBIT' THEN 1 ELSE -1 END, 0) AS balance_minor
  FROM accounts a LEFT JOIN postings p ON p.account = a.code
 GROUP BY a.code, a.normal_side
 ORDER BY a.code;
```

Query 1, the **trial balance**: for every account, the raw sum of its postings and its balance on its normal side. `LEFT JOIN postings p ON p.account = a.code` keeps accounts that have no postings. `COALESCE(x, 0)` replaces `NULL` by 0. `CASE a.normal_side WHEN 'DEBIT' THEN 1 ELSE -1 END` is a switch that gives 1 or -1 so credit-normal balances read positive. `GROUP BY` makes one row per account and `ORDER BY` sorts.

```sql
\echo '== 2. The ledger invariant: the grand total of every posting (must be 0), and entries that are not balanced pairs (none)'
SELECT COALESCE(sum(amount_minor), 0) AS ledger_sum_minor FROM postings;
SELECT entry_id, count(*) AS rows, sum(amount_minor) AS total
  FROM postings GROUP BY entry_id HAVING count(*) <> 2 OR sum(amount_minor) <> 0;
```

Query 2 has two statements. The first returns the grand total of every posting, which must be 0. The second looks for entries that are not balanced pairs: `GROUP BY entry_id HAVING count(*) <> 2 OR sum(amount_minor) <> 0` keeps only groups that break the rule; it must return no rows.

```sql
\echo '== 3. Captured payments per UTC day: count, gross, fees (the ledger side of a reconciliation)'
SELECT captured_at::date AS day, count(*) FILTER (WHERE state = 'CAPTURED') AS captured,
       sum(amount_minor) FILTER (WHERE state = 'CAPTURED') AS gross_minor,
       sum(fee_minor) FILTER (WHERE state = 'CAPTURED') AS fees_minor,
       count(*) FILTER (WHERE state = 'DUPLICATE_REVERSED') AS reversed_duplicates
  FROM payments GROUP BY 1 ORDER BY 1;
```

Query 3, the ledger side of a reconciliation: captured payments per UTC day. `captured_at::date` casts a timestamp to a date. `count(*) FILTER (WHERE state = 'CAPTURED')` counts only the rows meeting the condition; the same filter is used for the gross and fee sums, and `DUPLICATE_REVERSED` rows are counted separately. `GROUP BY 1` groups by the first selected column.

```sql
\echo '== 4. Provider transaction ids with more than one active payment (the duplicate break; none after resolution)'
SELECT provider_txn_id, count(*) AS active_payments, array_agg(source ORDER BY captured_at) AS sources
  FROM payments WHERE state = 'CAPTURED'
 GROUP BY provider_txn_id HAVING count(*) > 1;
```

Query 4: provider transaction ids with more than one active payment, the duplicate break. `array_agg(source ORDER BY captured_at)` collects the sources into a list, oldest first. It returns nothing once the duplicates are resolved.

```sql
\echo '== 5. Payments without their capture rows: an active payment must have six postings (four when the fee is 0); no rows'
SELECT pay.id, pay.provider_txn_id, count(p.id) FILTER (WHERE e.operation = 'CAPTURE') AS capture_postings
  FROM payments pay
  LEFT JOIN journal_entries e ON e.payment_id = pay.id
  LEFT JOIN postings p ON p.entry_id = e.id
 GROUP BY pay.id, pay.provider_txn_id, pay.amount_minor, pay.fee_minor
HAVING count(p.id) FILTER (WHERE e.operation = 'CAPTURE')
       <> 2 + CASE WHEN pay.amount_minor - pay.fee_minor > 0 THEN 2 ELSE 0 END
           + CASE WHEN pay.fee_minor > 0 THEN 2 ELSE 0 END;
```

Query 5: payments missing their capture rows. An active payment must have six capture postings, or four when the fee is 0, or only two if the net is 0. The query joins payments to their entries and postings, counts the capture postings and keeps payments where the count differs from `2 + (2 if net > 0) + (2 if fee > 0)`. It must return no rows.

```sql
\echo '== 6. Breaks by cause and status (every run)'
SELECT cause, status, count(*) AS breaks FROM reconciliation_breaks GROUP BY cause, status ORDER BY cause, status;
```

Query 6: breaks by cause and status over every run.

```sql
\echo '== 7. The worklist: breaks that need a person, oldest first'
SELECT run_date, provider_txn_id, cause, ledger_amount_minor, settlement_amount_minor, note
  FROM reconciliation_breaks WHERE status = 'NEEDS_REVIEW' ORDER BY run_date, provider_txn_id;
```

Query 7: the worklist, breaks with status `NEEDS_REVIEW`, oldest first.

```sql
\echo '== 8. Timing differences still waiting for a report, and how long they have waited'
SELECT provider_txn_id, run_date, (current_date - run_date) AS days_waiting
  FROM reconciliation_breaks WHERE status = 'CARRIED' ORDER BY run_date;
```

Query 8: timing differences still waiting. `current_date - run_date` is the number of days as a whole number.

```sql
\echo '== 9. Each run: the first-pass numbers'
SELECT run_date, settlement_rows, settled_total_minor, refunded_total_minor, clean_transactions, clean_total_minor, break_count
  FROM reconciliation_runs ORDER BY run_date;
```

Query 9: the first-pass numbers of each run.

```sql
\echo '== 10. What the resolutions posted, by operation'
SELECT e.operation, e.leg, count(DISTINCT e.id) AS entries, sum(p.amount_minor) FILTER (WHERE p.amount_minor > 0) AS debits_minor
  FROM journal_entries e JOIN postings p ON p.entry_id = e.id
 WHERE e.operation <> 'CAPTURE'
 GROUP BY e.operation, e.leg ORDER BY e.operation, e.leg;
```

Query 10: what the resolutions posted. It joins entries to postings, leaves out the original captures (`<> 'CAPTURE'`), groups by operation and leg, and counts the distinct entries and the debit total (`sum(...) FILTER (WHERE amount > 0)`).

## Mistakes people make

- **Forgetting `LEFT JOIN`.** An inner join would drop accounts with no postings from the trial balance.
- **Reading `<>` as an error.** It is SQL's "not equal".
- **Treating `NULL` as zero.** `sum` of nothing is `NULL`; `COALESCE` supplies the 0.

## Check yourself

1. What does `HAVING` do that `WHERE` cannot? *Filters groups after aggregation.*
2. Why does the seed's last line matter? *`COMMIT` runs the deferred balance checks for every inserted entry.*
3. What does `\echo` do? *It is a psql command that prints a label; it is not SQL.*
4. What should queries 2 (second part), 4 and 5 return? *No rows.*
5. Which fee does the sample file change? *That of `ptx_s0002`: 0.60 against the 0.52 recorded.*
